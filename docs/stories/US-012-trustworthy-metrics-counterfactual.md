## 用户故事

> **作为**要拿这份报告做决策的人，
> **我想要**指标不是"看着好"的平均数——成本要按真实分布算、延迟要有分位数、pass^k 要用**重复运行实测**、
> 还要能看到**分层**（整体好但难例很差要暴露出来）；归因要过一遍**反事实**，
> **以便于**我不被平均数骗，也不把"相关"当成"原因"。

## 验收标准（Given / When / Then）

### AC-1 真实成本，而非预汇总
- **假设** 每个用例都有自己的成本
- **那么** Cost-of-Pass = 总成本 / 通过数（由逐案例成本算出，不接受上游一个数字）

### AC-2 延迟看分布
- **那么** 延迟给出 p50 / p95 / p99，护栏用 p95 判定（不用平均数）

### AC-3 pass^k 实测
- **假设** 同一用例跑了 k 次
- **那么** 只有 **k 次全过** 才算可靠，指标标明"实测"口径；没有重复运行时才回落外推，并注明是独立性假设

### AC-4 分层暴露真相
- **当** 我看 demo 报告
- **那么** 「分层指标」显示整体成功率 72%，但 **hard 层只有 15%**，最差层标红；幻觉/拒答也集中在 hard 层

### AC-5 归因过反事实
- **假设** 技术侧占了 80% 的问题
- **那么** 技术侧被标 `counterfactualVerified`（修好它残余 ≤20%）
- **并且** 若两方各占一半，**谁都不被标注**（不把相关当因果）
- **并且** 报告写明这是数据级充分性检验，不是重跑

## 不在本故事内
- REFLECT 真重跑（需执行层）；分层各自的置信区间；分层门禁策略；pass^k 无偏估计/功效校正。

## 演示脚本
1. `pnpm --filter @tengxiaohtx/metrics test`：分位数 / Cost-of-Pass / pass^k 实测 / 分层。
2. `pnpm --filter @tengxiaohtx/ingest test`：轨迹（含 case_id 重复运行、成本、耗时、difficulty tag）端到端产出上述指标。
3. `pnpm --filter @tengxiaohtx/attribution test`：单因标注 / 双因都不标 / 无失败不标。
4. 打开 demo → 「分层指标（诊断）」看 整体 72% vs hard 15.15%（最差层红框）。
